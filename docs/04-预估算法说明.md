## 一、为什么必须做预估

游戏买量生意的现金流形状是**「今天流出、未来 90~360 天回流」**：

| 时间 | 发生什么 | 会计影响 |
|---|---|---|
| 投放当天（T+0） | 媒体账户中的钱被消耗掉 | **成本立刻发生**（经营口径计入当日） |
| 充值当天（每周） | 向媒体账户充值 | **现金立刻流出**（账面口径计入） |
| 投放后 D1~D30 | 新增用户产生广告展示 / 内购 | 收入只回来一小部分（约 17%~88%） |
| 投放后 D30~D90 | 留存用户持续贡献 | 收入回到约 88%~112% |
| 投放后 D60~D60+45/30 天 | 平台/渠道结算并打款 | **账面收入才到账**，比收入发生晚 30~60 天 |

由此产生三个不可回避的事实：

1. **账面严重滞后**：`已到账收入 − 充值支出` 在这段时间天然是负数。实测默认期间（2025-07~2026-06）账面利润 **−168.4 万元**，而经营利润 **+2307.8 万元**，口径差额 **+2476.2 万元**。差额不是「问题」，而是**已投出去、正在回收路上的钱**。只看账面，会误判成公司在亏钱。
2. **成本与收入必须在同一期间匹配**：投放花掉的 100 万，换来的是未来 360 天的收入。若把 100 万全部记在本月、收入按到账日记在未来几个月，任何一个月都算不出真实经营质量。这就是必须做**权责发生制**（accrual）的原因。
3. **决策要等不起**：投放策略调整周期是「天/周」，财务结算周期是「月」。等结算数据回来后才发现某个游戏亏了，钱已经花掉。所以必须用**回收曲线**把未来收入提前确认，让决策者在 D30 就能看到这笔投放最终会赚还是赔。

**一句话**：本看板的经营利润 = 投资额 + 预估回报率，服务的是「这笔生意最终赚不赚钱」；账面利润服务的才是「账上现在有多少钱」。

## 二、回收曲线的数学形式与推导

### 2.1 对数曲线（主用）：`ROI(n) = curveA · ln(n) + curveB`

```text
ROI(n) = curveA · ln(n) + curveB        n = 投放后天数（n ≥ 1），返回值 = 累计回收倍数（1.0 = 回本）
dROI/dn = curveA / n  > 0              永远单调递增（回收持续发生）
d²ROI/dn² = −curveA / n² < 0           边际增速递减（前期爬得快，后期趋平）
```

| 参数 | 数学含义 | 业务含义 | 本看板取值来源 |
|---|---|---|---|
| `curveB` | `ROI(1)`（因 `ln(1)=0`） | **首日回收率**，代表素材/版位/变现效率的「起跑线」 | 每个游戏独立配置（`dim_game.curve_b`） |
| `curveA` | 单位 `ln(n)` 带来的 ROI 增量 | **爬升速度**，越大说明长线留存/LTV 越好、回本越快 | 每个游戏独立配置（`dim_game.curve_a`） |

**边界与兜底（代码事实）**：

- `n <= 0` → 返回 `0`（`roiAt` 首行判断）
- `curveA·ln(n) + curveB < 0` → 被 `Math.max(0, …)` 截断为 0，因此 ROI 永不为负
- 曲线参数缺失时回退 `curveA = 0.2, curveB = 0.15`

**标准参数的曲线形状（`curveA=0.21, curveB=0.17`，可由 `roiAt()` 直接复现）**：

| 投放后天数 n | 1 | 3 | 7 | 15 | 30 | 60 | 90 | 180 | 360 |
|---|---|---|---|---|---|---|---|---|---|
| 累计 ROI | 0.170 | 0.401 | 0.579 | 0.739 | 0.884 | 1.030 | **1.115** | 1.260 | 1.406 |

边际回收率（`f(k) = ROI(k) − ROI(k−1)`，即第 k 天新回收的收入占比）：

| k | 1 | 2 | 3 | 7 | 30 | 90 | 180 | 360 |
|---|---|---|---|---|---|---|---|---|
| `f(k)` | 0.1700 | 0.1455 | 0.0863 | 0.0470 | 0.0151 | 0.0056 | 0.0030 | 0.0015 |

可以看到 `f(k)` 单调递减且趋于 0：D1 一天就回收 17%，D90 之后每天只回收 0.56%。这正是「先快后慢」的买量回收规律。

### 2.2 两点标定法（如何从业务锚点反推参数）

业务方通常能给出**两个锚点**：首日 ROI `r₁` 与 N 日 ROI `r_N`。因为 `ln(1) = 0`，可直接解出：

```text
已知 (1, r₁) 与 (N, r_N)：
    curveB = r₁                              ← 直接得到，无需拟合
    curveA = (r_N − r₁) / ln(N)              ← 由 r_N = curveA·ln(N) + r₁ 移项

反过来，知道 curveA/curveB 后：
    N 日 ROI    = curveA·ln(N) + curveB
    达到目标 ROI* 所需天数（回本天数）：
        n* = exp((ROI* − curveB) / curveA)   ROI*=1 时为 exp((1 − curveB)/curveA)
```

**数值验算（业务锚点 D1 = 20%、D90 = 105%）**：

```text
curveA = (1.05 − 0.20) / ln(90) = 0.85 / 4.4998 = 0.1889
curveB = 0.20

检验：ROI(90) = 0.1889 × ln(90) + 0.20 = 0.85 + 0.20 = 1.05  ✓ 与锚点一致
```

| 天数 | D1 | D3 | D7 | D30 | D60 | D90 | D180 | D360 |
|---|---|---|---|---|---|---|---|---|
| 锚点曲线 ROI | 0.200 | 0.408 | 0.568 | 0.843 | 0.973 | **1.050** | 1.181 | 1.312 |
| 本看板标准曲线 ROI | 0.170 | 0.401 | 0.579 | 0.884 | 1.030 | **1.115** | 1.260 | 1.406 |

两条曲线在 D3/D7/D30 上高度接近（差异 < 5 个百分点），说明 `curveA≈0.21, curveB≈0.17` 与业务锚点**同量级、同形状**，可用于互换标定。

### 2.3 与现有系统的对齐

现有系统的「预估 90 日 ROI」锚点为：**D1≈20% / D3≈33% / D7≈48% / D90≈105%**。
本看板标定曲线（`curveA≈0.21, curveB≈0.17`）给出：**D1≈17% / D3≈40% / D7≈58% / D90≈112%**。

| 锚点 | 现有系统 | 本看板标准曲线 | 差异 | 判定 |
|---|---|---|---|---|
| D1 | 20% | 17% | −3 pt | 一致 |
| D3 | 33% | 40% | +7 pt | 一致（量级相同） |
| D7 | 48% | 58% | +10 pt | 一致（量级相同） |
| D90 | 105% | 112% | +7 pt | 一致 |

**结论：本站的曲线在量级与形状上与现有系统一致，差异主要来自 D1 略低、中期爬升略快**（对数曲线在前期比业务直觉更陡）。若要与现有系统完全对齐，用 §2.2 的两点标定法取 `curveA = 0.1889, curveB = 0.20` 即可。

### 2.4 幂律备选：`ROI(n) = p · n^q`

```text
两点（x₁,y₁）(x₂,y₂) 拟合：
    q = (ln y₂ − ln y₁) / (ln x₂ − ln x₁)
    p = y₁ / x₁^q

对应实现：fitPower(d1, v1, d2, v2) → { p, q }
曲线取值：roiAtPower(n, p, q) = max(0, p · n^q)
```

**数值例**：用标准曲线的 `(1, 0.170)` 与 `(90, 1.115)` 两点拟合：

```text
q = (ln 1.115 − ln 0.170) / (ln 90 − ln 1) = (0.10883 − (−1.77196)) / 4.49981 = 0.4180
p = 0.170 / 1^0.4180 = 0.170
→ ROI(n) = 0.170 · n^0.4180
```

| 天数 | D1 | D7 | D30 | D90 | D180 | D360 |
|---|---|---|---|---|---|---|
| 对数曲线 | 0.170 | 0.579 | 0.884 | 1.115 | 1.260 | 1.406 |
| 幂律曲线 | 0.170 | 0.383 | 0.704 | 1.115 | **1.490** | **1.990** |

**形状差异（选型依据）**：

| 特征 | 对数 `a·ln n + b` | 幂律 `p·n^q` |
|---|---|---|
| 关键点重合 | D1、D90 相同 | D1、D90 相同 |
| 前期（D1~D30） | 爬得**更快**（D7 高 51%） | 更慢 |
| 中期（D30~D90） | 略慢 | 接近线性 |
| 后期（D90 之后） | **更平**（D360 1.41） | **更陡**（D360 1.99，长尾更肥） |
| 极限行为 | `n→∞` 时对数发散但极缓；实务上等于「回收永不停止」 | 幂律无上界，长尾预测更激进 |
| 适用判断 | 变现以「新用户首周行为」为主、长线留存一般的买量模型 | 变现依赖长线留存 / 社交裂变 / IP 生命周期极长的产品 |

**工程建议**：默认用对数曲线（更保守、更贴合现有系统）；幂律仅作为**对照实验**在参数配置页展示（`roiAtPower` / `fitPower` 已导出，就是给参数配置页做曲线对照用的）。**不要**在同一个看板期间混用两套曲线做汇总，否则口径不可解释。

## 三、逐日回收增量的卷积算法

单日投放 `spend(d)` 产生的收入不是一次性到账，而是按 `f(1), f(2), f(3)…` 分摊到投放之后每一天。于是**第 t 天的应确认收入**等于所有历史投放日在 t 这一天的回收增量之和：

```text
f(k) = ROI(k) − ROI(k−1)                        k ≥ 1，投放后第 k 天的边际回收率
                                                 （f(1) = ROI(1) = curveB）

accrual(t) = Σ_{d ≤ t} spend(d) · f(t − d)      第 t 天的应确认收入（权责发生制）
```

这就是一个**因果卷积**：把投放序列 `spend(·)` 与回收核 `f(·)` 做卷积。代码实现（`store.ts` 的 `SERIES` 构造块）：

```ts
// 先算核（按游戏缓存，Float64Array，长度 RECOVERY_MAX_DAY + 1 = 366）
for (let k = 1; k <= 365; k++) { const cur = roiAt(k, a, b); rate[k] = max(0, cur − prev); prev = cur; }
// 再做卷积：每天向未来 k 天累加 spend(d) · f(k)
for (let d = startIdx; d <= endIdx; d++) {
    const s = spend[d];  if (s <= 0) continue;
    const limit = Math.min(365, DAY_COUNT − 1 − d);     // 核长截断 + 数据边界截断
    for (let k = 1; k <= limit; k++) accrual[d + k] += s * f[k];
}
```

### 3.1 为什么复杂度是 O(天数 × 365)，以及优化方向

| 维度 | 当前实现 | 数值 |
|---|---|---|
| 组合数 | `CAMPAIGNS` | 84 个（游戏 × 平台 × 投手） |
| 卷积步数 | 每个组合每个投放日最多 365 次 | ≤ 900 × 365 ≈ 32.9 万次/组合 |
| 总运算量 | 84 × 32.9 万 | ≈ 2.8 × 10⁷ 次浮点累加（构建期一次性） |
| 实际耗时 | 单线程构建 + 按游戏缓存核（`RATE_CACHE`） | 浏览器端毫秒~百毫秒级，可接受 |

**工程优化方向**（按收益排序）：

1. **按游戏归并再卷积**：收入确认只依赖 `gameId`（核）与消耗总量，可先按 `游戏 × 日` 汇总消耗（84 → 16 条序列），再卷积 → 运算量降 5 倍以上，结果完全等价。
2. **FFT 卷积**：卷积长度 900 + 365，用 FFT 做 O(N log N) 卷积，适合日粒度数据量再放大 100 倍时。
3. **前缀和 / 分块**：对数核 `f(k) = a·ln(k/(k−1))` 是平滑缓变的，可对 `k > 90` 的低贡献段做**分段线性近似**（D90 后每天只贡献 0.56%，误差可忽略）。
4. **落库做增量**：真实落地时应在数仓侧一次性算出 `accrual`，看板只读结果（见 `docs/03` §5 的 `ads_operating_metrics_monthly`），前端不再做卷积。

### 3.2 与到账收入（账面口径）的关系

```text
cash(t) = accrual(t − lag)            lag = platform.settleLagDays
```

| 平台 | `settleLagDays` | 含义 |
|---|---|---|
| 腾讯广告 | 45 天 | 账面收入比应计收入晚 45 天 |
| 巨量引擎 | 30 天 | 晚 30 天 |
| 快手磁力 | 30 天 | 晚 30 天 |
| 小米营销 | 60 天 | 晚 60 天 |

> 因此当前数据末端（2026-06-18）往前 45~60 天的收入**还没有到账**，这部分就是 `receivable`（应收未收）的主体，也是账面利润与经营利润差额的主要来源。

### 3.3 充值（预付）在原型中的生成规则

账面口径的现金流出用充值额 `prepay` 表示。原型规则（每 7 天充值一次，向上取整到万元）：

```text
prepay(d) = ceil( (Σ_{k=d}^{d+6} spend(k) × 1.05) / 10000 ) × 10000      d ≡ startIdx (mod 7)
```

即「按周预留 5% 缓冲额度」。实测全期：投放消耗 **15149.5 万元**，充值额 **17736.0 万元**，差额即预付余额增长。

## 四、权责发生制的收入确认

### 4.1 公式

本期（月/季/年）应确认收入由两部分组成：**本期投放产生的回收** + **历史 cohort 在本期的新回收**。

```text
本期应确认收入 = Σ_{d ∈ 本期} spend(d) · [ ROI(T_end − d) − ROI(T_start − d) ]
               + Σ_{d < T_start} spend(d) · [ ROI(T_end − d) − ROI(T_start − d) ]
             = Σ_{所有 d ≤ T_end} spend(d) · [ ROI(T_end − d) − ROI(T_start − d) ]

其中 T_start / T_end = 本期首日 / 末日相对该投放日的天数（T_start − d ≤ 0 时取 ROI(0) = 0）
```

直观理解：**本期确认额 = 期末累计应回收 − 期初累计应回收**（增量法），这正是 `accrual(t) = Σ spend(d)·f(t−d)` 在区间上的累加。

### 4.2 数值例子

设某游戏 `curveA = 0.21, curveB = 0.17`，两笔投放：

| 投放 | 日期 | 金额 |
|---|---|---|
| A | 2025-12-10 | 100 万元 |
| B | 2026-01-15 | 200 万元 |

计算 **2026 年 1 月**（T_start = 2026-01-01，T_end = 2026-01-31）应确认收入（示例值，按自然日差近似）：

```text
投放 A（2025-12-10 投，2026-01-01 时已投 22 天；1-31 时已投 52 天）
  期初累计 ROI(22) = 0.21·ln(22)+0.17 = 0.21×3.0910+0.17 = 0.8191
  期末累计 ROI(52) = 0.21·ln(52)+0.17 = 0.21×3.9512+0.17 = 0.9998
  本期确认 = 100 万 × (0.9998 − 0.8191) = 18.07 万元

投放 B（2026-01-15 投；月末已投 16 天）
  本期确认 = 200 万 × ROI(16) = 200 × (0.21×ln(16)+0.17) = 200 × 0.7523 = 150.46 万元

2026 年 1 月应确认收入 = 18.07 + 150.46 = 168.53 万元
其中「历史 cohort 新回收」占 18.07 / 168.53 = 10.7%
```

**对应成本与利润**：

```text
本期经营利润 = 168.53 − 本期投放消耗 − 人工成本 − 管理费用
```

注意投放 A 的 100 万元成本发生在 **2025 年 12 月**，而它带来的收入在 12 月只确认了 `100 × ROI(21) = 81.78 万元`，剩下 18.22 万元分在 2026 年及以后。**成本与收入的期间错配，正是必须用曲线做时间匹配的根本原因。**

### 4.3 三个重要的存量指标（时点口径）

| 指标 | 公式 | 业务含义 | 实测（默认期间） |
|---|---|---|---|
| 预付余额 | `max(0, 累计充值 − 累计消耗)` | 在媒体账户里的**未消耗现金**，是资产不是费用 | 5108.3 万 |
| 应收未收 | `max(0, 累计预估总回收 − 累计已确认回收)` | 存量用户的**未来价值**，尚未确认 | 3071.6 万 |
| 现金缺口 | `预付余额 + 应收未收` | 已花出去、还在路上、尚未变成「已确认利润」的钱 | 8179.96 万 |

## 五、月度滚动预估的三层算法

对应代码 `buildForecast(filter, horizon = 6)`。输出结构 `ForecastPoint{ month, label, actual, revenue, cost, profit, optimistic, pessimistic, confidence }`。

### 5.1 L1 · 当月实时预估（`actual = false, confidence = 0.86`）

**当前口径（与未来月完全同源）**：

```text
elapsed = DAYS_ELAPSED / DAYS_IN_MONTH                        （2026-06: 18 / 30 = 0.6）

全月收入     = recoveryOfMonth(CURRENT_MONTH_IDX, projectCurrent = true)
               ← 该自然月窗口内、全部 cohort 的确认回收；其中**当月消耗按已过天数折算成整月**
                 消耗_整月 = 当月实际消耗 / elapsed
               ← 不再使用「已实现收入 × 补足系数」这类近似
全月可变成本 = 当月实际消耗 / elapsed                          （即折算后的整月消耗）
全月固定成本 = 整月人工 + 整月管理费用                          （整月都会发生，不摊薄）
全月利润     = 全月收入 − 全月可变成本 − 全月固定成本
三档情景     = 利润 ± 收入 × σ,  σ = 0.10；悲观用 1.15σ
```

**为什么改成这样（三段演进，都是踩过的坑）**：

| 版本 | 做法 | 问题 |
|---|---|---|
| v1 | `已实现收入 × [1 + (ratio−1) × 0.88]` | 用一个拍出来的系数 0.88 近似「剩余天数还能回收多少」，与未来月用的卷积口径不同源 → 当月预估与未来月预估**不可直接比较** |
| v2 | 当月成本按 `[1 + (ratio−1) × 0.35]` 外推 | 同样的问题：固定成本（工资、办公费）本来就该按整月计入，用「系数外推」等于对固定成本做了二次近似 |
| **v3（当前）** | **收入走同一套窗口卷积**（当月消耗折算整月后作为输入）＋ **可变成本按天数折算** ＋ **固定成本取整月** | 当月预估与未来月预估**同源、可比较**，且每一项都有明确的会计含义 |

**实测核对（2026-06，默认筛选，单位：万元）**：

| 项 | 计算 | 全月预估 |
|---|---|---|
| 全月收入 | `recoveryOfMonth(2026-06, true)` | **1787.8** |
| 全月可变成本 | 当月实际消耗 734.07 ÷ 0.6 = 1223.4 | 1223.4 |
| 全月固定成本 | 整月人工 383.2 + 整月管理 37.8 | 421.0 |
| 全月成本合计 | 1223.4 + 421.0 | **1644.4** |
| **全月经营利润** | 1787.8 − 1644.4 | **+143.4** |
| 乐观 | `143.4 + 1787.8 × 0.10` | **+322.2** |
| 悲观 | `143.4 − 1787.8 × 0.10 × 1.15` | **−62.2** |

对照「当月已实现」（截至 6 月 18 日，固定成本按 0.6 摊薄）：应计收入 1033.0 万、消耗 734.1 万、人工 229.9 万、管理 22.7 万、经营利润 **+46.3 万**。

> ⚠️ **两个数不矛盾，是两种口径**：
> - **已实现 46.3 万** = 只算 18 天里真正发生的收入与摊薄到 18 天的固定成本 → 回答「**到现在为止赚了多少**」；
> - **全月预估 143.4 万** = 把 18 天的消耗折算成整月后走完整卷积，再加上整月固定成本 → 回答「**这个月最终会是多少**」。
>
> 早期版本因为没有对固定成本做摊薄，导致「已实现」被整月固定成本压成大额负数（当时实测 −122 万元），与「全月预估」自相矛盾，被误读为数据错误。现在两套口径都在引擎里显式实现（`prorationOf()` 负责摊薄、`rawCostOfIds()` 负责整月），不会再混。

**σ 的定义（重要）**：当月的 σ 是**固定 0.10**，**不随预测月序号增长**；只有未来月才用 `σ(h) = 0.1 + 0.022h`。

### 5.2 L2 · 未来月份预估（`confidence` 按 §5.5 衰减）

**未来月只做一件事：算这个自然月自己的账**。收入用与数据引擎**完全相同的窗口卷积**，不再有任何近似式：

```text
对预测月 mi：
  窗口 = [该月 1 号, 次月 1 号)                        winStart = monthFirstDay(mi)
                                                       winEnd   = monthFirstDay(mi + 1)
  revenue(mi) = Σ_{投放月 src = 0 … mi} Σ_{组合} spend(src) × [ ROI(t1) − ROI(t0) ]
                 其中 t0 = clamp(winStart − srcMid, 0, 365)
                      t1 = clamp(winEnd   − srcMid, 0, 365)
                     srcMid = 该投放月的月中代表日

  newSpend(mi) = trailingSpend × (SEASON[mi 月份] / 1.02)      ← 该月预计投放
  cost(mi)     = newSpend(mi) + (人工 + 管理费用) × 1.012^h     ← 固定成本按月 +1.2%
  profit(mi)   = revenue(mi) − cost(mi)
```

**关键实现要点**：

| 要点 | 说明 |
|---|---|
| **窗口是「该自然月自己的窗口」** | `[月初, 次月初)`，因此**逐月之间不会重复计入**。早期版本用「从数据截止日累计到该月」的窗口，导致同一笔回收被连续几个月重复确认，预估值随预测期**单调漂移**（越远的月份虚高越多） |
| **消耗序列必须覆盖 3 类月份** | `trial(cid, src)`：① 已发生月取实际消耗；② 当月取 `实际 / elapsed`（折算整月）；③ **未来月取「近 3 个完整月均值 × 预算/季节」**。三者拼起来才是完整的 `src = 0 … mi` 序列 |
| 基线只取**完整月** | `trailingIdxs` = 最近 3 个 `mi < CURRENT_MONTH_IDX` 的月份。**当月只过了一部分，纳入会把基线拉低** |
| 季节系数 | `SEASON[12] = [1.06, 0.82, 0.98, 1.00, 1.02, 1.05, 1.12, 1.14, 1.00, 1.08, 1.16, 1.10]`，除以均值 1.02 做归一，避免整条曲线被系统性抬高或压低 |
| 成本月增 | `1.012^h`（每月 +1.2%）。工资每年调薪约 6%（`Math.pow(1.06, year − 2024)`）折算到月约 0.49%，叠加社保基数上调与人头增长，取 1.2%/月作为保守上界 |
| **未来月可以超出 `MONTHS` 范围** | 早期实现有 `if (mi >= MONTH_COUNT) break;`，而 `MONTHS` 的末月恰好就是当月 → **未来滚动预估永远为空**。现改为 `monthKeyOf(mi)` 合成 `MONTHS` 之外的月份键 |

**实测结果**：`store.forecast(defaultFilter(), 6)` 返回 **18 条** = 11 个实际月（2025-07 ~ 2026-05）+ 当月预估（2026-06）+ 未来 6 个月（2026-07 ~ 2026-12）。

|---|---|---|---|---|---|---|---|

| **2026-06** | 当月预估 | 1787.8 | 1644.4 | **143.4** | 322.2 | −62.2 | 86% |

### 5.3 L3 · 三档情景（中性 / 乐观 / 悲观）

```text
σ(h) = 0.10                h = 0（当月）
σ(h) = 0.10 + 0.022 × h     h = 1, 2, 3, …（未来月）

乐观 = 利润 + 收入 × σ(h)
悲观 = 利润 − 收入 × σ(h) × 1.15
```

| σ | 当月 | h=1 | h=2 | h=3 | h=4 | h=5 | h=6 |
|---|---|---|---|---|---|---|---|
| 取值 | 10.0% | 12.2% | 14.4% | 16.6% | 18.8% | 21.0% | 23.2% |
| 区间宽度（相对收入） | ±10.0% / −11.5% | +12.2% / −14.0% | +14.4% / −16.6% | +16.6% / −19.1% | +18.8% / −21.6% | +21.0% / −24.2% | +23.2% / −26.7% |

**为什么用 `利润 ± 收入 × σ` 而不是 `利润 × (1 ± k)`**：

```text
❌ 旧写法：乐观 = 利润 × 1.10，悲观 = 利润 × 0.86
   当利润为负时方向反转：利润 = −100 → 乐观 = −110，悲观 = −86
   结果「乐观情景比悲观情景更差」，图上的上下轨会交叉，业务方直接看懵。

✅ 新写法：乐观 = 利润 + 收入 × σ，悲观 = 利润 − 收入 × σ × 1.15
   当利润为负时仍然满足 乐观 > 悲观，且利润 = 0 时区间对称于 0。
```

**三条设计理由**：

1. **不确定性的载体是「收入」而不是「利润」**：成本（消耗、工资）是已决策 / 已签合同的，波动远小于收入。所以区间宽度正比于 `revenue`。这带来一个有用的性质：**利润接近 0 时区间对称**，且**利润为负时不会方向反转**。
2. **σ 随预测月线性增长**：越远越不确定，且业务上远处的偏差来源是**累积且不可逆**的（一次平台政策变化会同时影响之后所有月份），所以用线性扩张而非平方根扩张。
3. **悲观额外 ×1.15**：坏消息的尾部比好消息更肥——一次封号 / 一次审核失败 / 一次渠道下调分成，损失远大于同等概率的利好。

### 5.4 `store.project()` · 经营推演模拟器（what-if 沙盒）

```ts
store.project(filter, {
  horizon: number;        // 推演月数
  spendScale: number;     // 投放预算倍率，1.2 = 预算 +20%
  curveAScale: number;    // 回收曲线 curveA 倍率（1.1 = 爬升更快）
  curveBScale: number;    // 回收曲线 curveB 倍率（1.05 = 首日回收率上浮 5%）
  laborScale: number;     // 人工 / 管理费用倍率（0.9 = 裁员降本 10%）
  platformIds?: string[]; // 只推演这些平台（空 = 全部）
  gameIds?: string[];     // 只推演这些游戏（空 = 全部）
}) : Array<{ month, label, spend, revenue, cost, profit }>
```

| 口径 | 实现 |
|---|---|
| 收入 | 与 `buildForecast` **同一套自然月窗口卷积**：`Σ_组合 Σ_{src≤mi} spend(src) × [ROI(t1, a·curveAScale, b·curveBScale) − ROI(t0, …)]` |
| 消耗（历史） | 已发生月取实际；当月取 `实际 / elapsed`（折算整月） |
| 消耗（未来） | `该组合近 3 个完整月月均消耗 × spendScale × SEASON/1.02` |
| 成本 | `该月消耗 + (人工 + 管理费用) × laborScale × 1.012^h`；固定成本基数取近 3 个完整月最后一月的**整月**值 |
| 平台/游戏限定 | `platformIds` / `gameIds` 只筛**受推演影响的投放组合**；固定成本仍按组织范围全额计入（这一点与 `forecast` 一致） |

**关键性质**：`spendScale = 1, curveAScale = 1, curveBScale = 1, laborScale = 1` 时，`project()` 就是「无干预基线」。

**⚠️ 为什么这个 API 必须放在引擎里（而不是让推演页自己算）**：推演页若自己另写一套近似式（例如「新增投放 × ROI(15 天) + 存量回看 ÷ 6」），会与窗口卷积产生**系统性偏差**——早期实测约 **40% 的收入低估**，导致推演页全部情景显示亏损，而预估页显示盈利，**同一家公司两个页面结论相反**。这类矛盾一旦出现在汇报现场，整套数字的可信度就没了。因此本 API 的注释里明确写了设计意图：**提供唯一实现，两边同源**。

**`projectMonths()` 是未来月投影的唯一实现**：`buildForecast` 的未来月循环不再自己算 spend / 收入，而是直接复用 `projectMonths(filter, { horizon, spendScale: 1, curveAScale: 1, curveBScale: 1, laborScale: 1 })` 的结果，只在此基础上叠加三档情景与置信度衰减。两者在 `scale = 1` 时**逐月收入与成本完全一致（实测差额 0.00 万）**：

```ts
// buildForecast 内部（未来月部分）
const projected = projectMonths(filter, { horizon, spendScale: 1, curveAScale: 1, curveBScale: 1, laborScale: 1 });
for (let h = 1; h <= horizon; h++) {
    const { revenue, cost, profit } = projected[h - 1];   // 收入 / 成本 / 利润全部来自唯一实现
    // 仅此处叠加情景与置信度：
    // optimistic = profit + revenue * σ(h); pessimistic = profit − revenue * σ(h) * 1.15
}
```

> 历史背景（避免重踩）：在统一之前，`buildForecast` 的 `trial()` 与 `projectMonths` 的 `spendAt()` 是两份独立实现，两个细节不同就产生了 1%~9% 的月收入差：① 当月（2026-06）消耗是否按已过天数折算成整月；② 月份代表日取「月中」还是「被 `DAY_COUNT − 1` 截断后的中点」。**`projectMonths` 的取法（折算整月 + 月中）对未来月才是正确的**，因此以它为准，`forecast` 改为复用。修复后 2026-07 收入由 1708.5 万修正为 **1860.6 万**，未来 6 个月收入与成本差额全部归零。

### 5.5 置信度衰减

```text
置信度 = max(42%, 86% − 6% × h)
当月（h = 0） = 86%
已发生月份     = 100%（代码中 confidence = 1）
```

| 状态 | 已发生月 | 当月 | h=1 | h=2 | h=3 | h=4 | h=5 | h=6 | h=7 | h≥8 |
|---|---|---|---|---|---|---|---|---|---|---|
| 置信度 | 100% | 86% | 80% | 74% | 68% | 62% | 56% | 50% | 44% | 42%（下限） |

**设计理由**：当月已过 18/30 天，13 个维度的实际数据已经在手，剩余 12 天只是外推 → 86% 是「有实测锚点的不确定性」。每往后一个月，就多丢失一个月的实测锚点，且必须叠加一次「投放节奏假设」（消耗基线保持不变）与一次「回收效率假设」（曲线参数不变），两项假设的复合误差按月累积 → 每月 −6 个百分点。**42% 的下限**是工程兜底：再低的数字对决策没有信息量（等于「不知道」），保留 42% 至少表达「方向上仍有参考价值」。

## 六、Cohort（同期群）回收分析

### 6.1 定义

**Cohort = 同一个自然月内投放的全部组合集合**。跟踪这个 cohort 在投放后第 30 / 60 / … / 360 天的累计 ROI，就能回答「**每个月投出去的钱，到第 N 天收回多少**」——这是判断「放量节奏是否健康」最直接的视图。

### 6.2 计算方式（对应 `buildCohorts(filter, count = 8)`）

```text
1. 取最近 count 个「投放月」（最多到当月）
2. 对每个 cohort 月：cohortStart = 该月 1 日；cohortEnd = 该月 28 日 + 2 天
3. 累加该 cohort 内所有组合的消耗，并**按消耗加权**得到该 cohort 的等效曲线参数：
       a = Σ (spend_c × curveA_c) / Σ spend_c
       b = Σ (spend_c × curveB_c) / Σ spend_c
   权重 = 各游戏在该 cohort 的消耗，所以「重投的游戏」参数主导该月曲线
4. 对 day ∈ {30, 60, 90, 120, 150, 180, 210, 240, 270, 300, 330, 360}：
       roi(day) = roiAt(day, a, b)
       projected = (cohortStart + day) ≥ 数据末端日        ← 该点尚未由真实数据支撑，属纯预估
5. cohort 无消耗则跳过（不输出空点）
```

**实测示例（默认筛选）**：

| Cohort | 投放消耗 | D30 | D90 | D180 | D360 | `projected` 起始 |
|---|---|---|---|---|---|---|
| 2026-01 | 1397.1 万 | 0.8751 | 1.1041 | 1.2486 | 1.3930 | D180 |
| 2026-02 | 1095.9 万 | 0.8714 | 1.0995 | 1.2435 | 1.3874 | D150 |
| 2026-03 | 1239.1 万 | 0.8602 | 1.0856 | 1.2278 | 1.3700 | D120 |
| 2026-04 | 1270.1 万 | 0.8699 | 1.0977 | 1.2414 | 1.3851 | D90 |
| 2026-05 | 1224.1 万 | 0.8559 | 1.0803 | 1.2219 | 1.3636 | D60 |
| 2026-06 | 734.1 万 | 0.8624 | 1.0883 | 1.2308 | 1.3734 | D30 |

> Cohort 视角的细节一：2026-06 cohort 的 D30 已经标 `projected`，因为「6 月 1 日 + 30 天 = 7 月 1 日」超出了数据末端 2026-06-18。数据越新的 cohort，其曲线越早进入纯预估区间——这正是 §8 要讨论的局限之一。
>
> Cohort 视角的细节二：cohort 的消耗窗口是「该月 1 日 ~ 该月 28 日 + 2 天」而非完整自然月，因此 2026-01 cohort 的消耗是 **1397.1 万**，略小于「按整个自然月聚合」得到的 1448.5 万。这是代码 `cohortStart / cohortEnd` 的定义（用 28 日 + 2 天以规避不同月长），文档与代码一致。

### 6.3 预计回本天数（反解）

令 `ROI(n) = 1`：

```text
curveA · ln(n) + curveB = 1
ln(n) = (1 − curveB) / curveA
n = exp( (1 − curveB) / curveA )         ← 回本天数反解公式
```

**数值验证 1（标准曲线）**：

```text
curveA = 0.21, curveB = 0.17
n = exp((1 − 0.17) / 0.21) = exp(0.83 / 0.21) = exp(3.9524) = 52.1 天
反向校验：ROI(52.1) = 0.21 × ln(52.1) + 0.17 = 0.21 × 3.9532 + 0.17 = 1.0002 ≈ 1  ✓
```

**数值验证 2（用 2026-01 cohort 实测数据反解，再正向校验）**：

```text
已知 D30 = 0.8751、D90 = 1.1041
两点反解：curveA = (1.1041 − 0.8751) / (ln 90 − ln 30) = 0.2290 / 1.0986 = 0.2084
          curveB = 0.8751 − 0.2084 × ln(30) = 0.8751 − 0.7086 = 0.1661
回本天数：n = exp((1 − 0.1661) / 0.2084) = exp(4.0012) = 54.6 天
正向校验：ROI(30) = 0.2084 × 3.4012 + 0.1661 = 0.8750  ✓（与输入 0.8751 一致）
          ROI(90) = 0.2084 × 4.4998 + 0.1661 = 1.1040  ✓（与输入 1.1041 一致）
```

**业务读法**：该 cohort 预计 **55 天左右回本**，比标准曲线的 52.1 天略慢，说明这几个月投的游戏整体回收效率略低于公司标准参数。

## 七、模型校准与回测

### 7.1 MAPE（平均绝对百分比误差）

```text
MAPE = mean( |实际 − 预估| / 实际 )        滚动回测最近 6 个月
```

**为什么用 MAPE 而不是 RMSE**：看板服务于**跨游戏/跨平台横向对比**，各游戏消耗量级差 10 倍以上（月消耗从 101 万到 2212 万）。RMSE 会被大消耗游戏主导，MAPE 是尺度无关的，能让「小盘口预测得准不准」同样被看见。

**计算例**。「实际经营利润」一列**可由代码复现**：
`store.metricsOf(defaultFilter({startMonth:'YYYY-MM', endMonth:'YYYY-MM'}), 'company', 'company').profit`。
「当月预估」一列是**示例值**——原型仓库不保存历史预估留档（mock 数据是一次性确定性生成的），生产落地时必须在数仓按批次存 `forecast_snapshot`（每月固定日期跑一次 `forecast()` 落库），否则 MAPE 无法回溯计算。

| 月 | 实际经营利润（万元） | 当月预估（万元，示例值） | 绝对百分比误差 |
|---|---|---|---|
| 2024-07 | −85.0 | −78.5 | 7.6% |
| 2024-08 | −44.9 | −49.0 | 9.1% |
| 2024-09 | −67.3 | −80.7 | 19.9% |
| 2024-10 | 45.3 | 43.2 | 4.6% |
| 2024-11 | 51.9 | 49.8 | 4.1% |
| **MAPE（近 5 个月）** | | | **9.1%** |

> 上表实际值取自数据区间前段的月份，因为该段存在**亏损月**（负利润），正好展示一个工程注意点：
> **`MAPE = mean(|实际 − 预估| / 实际)` 在实际值为负或接近 0 时会失效**（分母为负会让误差符号翻转，分母接近 0 会让比值爆炸）。
> 落地时必须改用**对称口径**，三选一：
> ① 分母取绝对值：`mean(|实际 − 预估| / |实际|)`（最小改动，推荐）；
> ② 改用 **WAPE**：`Σ|实际 − 预估| / Σ|实际|`（对全公司层面更稳健）；
> ③ 改用 **sMAPE**：`mean(2|实际 − 预估| / (|实际| + |预估|))`（有界于 0~2，不会爆炸）。
>
> **行业参考**：买量回收预测的 MAPE 在 10%~20% 属正常；> 30% 说明曲线参数失真或投放结构发生突变，应触发重拟合。

### 7.2 偏差归因：区分「投放节奏偏差」与「回收效率偏差」

预估偏差 = 实际 − 预估，可**近似分解**为两项（因为收入 ≈ 消耗 × 回收率）：

```text
实际利润 − 预估利润 ≈ (实际消耗 − 预估消耗) × 预估回收率        ← 投放节奏偏差
                     + 实际消耗 × (实际回收率 − 预估回收率)      ← 回收效率偏差
                     （残差 = 两者交叉项，量级较小）
```

| 偏差类型 | 判别特征 | 业务含义 | 处置动作 |
|---|---|---|---|
| **投放节奏偏差** | 消耗偏离预估 > 15%，但 `实际ROI / 预估ROI` 在 0.95~1.05 | 计划改动、预算调整、账户被限流 → 曲线本身没问题 | 调 `trailingSpend` 与投放计划，**不动曲线参数** |
| **回收效率偏差** | 消耗基本符合预估，但 `实际ROI / 预估ROI` 偏离 > 10% | 素材老化、变现侧（eCPM/填充率）变化、版本更新 → **曲线失真** | 触发曲线重拟合（§7.3）；同时排查变现侧指标 |
| 混合偏差 | 两项都偏 | 通常是「为了冲量降质」——放量的同时 ROI 下滑 | 看单游戏层面：若 `forecastRoi < redLineRoi`，按预警建议压缩预算 |

**归因所需的两个可直接取到的量**：`Metrics.actualRoi`（累计已确认回收 / 累计消耗）与 `Metrics.forecastRoi`（累计预估总回收 / 累计消耗），它们的比值就是「回收效率实现度」。

### 7.3 参数按月重新拟合

**为什么必须按月重拟合**：`curveA` / `curveB` 是**经验参数**，会随以下因素漂移，长期不更新会系统性失真：

- 素材迭代（新素材首日 CTR 更高 → `curveB` 上移）
- 版本更新（新增付费点 → `curveA` 上移；改版导致流失 → `curveA` 下移）
- 平台政策（分成比例、结算规则变化 → 影响变现侧整体水平）
- 用户结构变化（新买量渠道人群质量差异 → 整条曲线平移）

**拟合方法（推荐两步）**。两种方法都输入**最近一个完整 cohort 的实测观测点**——即 `buildCohorts()` 输出的 `CohortPoint.roi`，它本身已按该 cohort 内各游戏的消耗加权，代表「这一个月整体投出去的钱」的回收表现：

```text
Step 1  两点标定（快速、可解释）：取该 cohort 的 D1 与 D30（或 D90）实测 ROI
            curveB = ROI(1)                                ← 实测首日回收率
            curveA = (ROI(N) − ROI(1)) / ln(N)
        优点：业务方能看懂、异常立刻暴露；缺点：只用了 2 个点，噪声敏感

Step 2  最小二乘回归（稳健）：用该 cohort 的 12 个观测点（D30…D360）对 ln(n) 做一元线性回归
            ROI(n) = curveA · ln(n) + curveB
            curveA = Cov(ln n, ROI) / Var(ln n)
            curveB = mean(ROI) − curveA · mean(ln n)
        优点：抗单点噪声；缺点：需要足够的观测天数（新 cohort 只有 D30/D60，权重需按天数加窗）
```

**上线节奏建议**：每月 T+5 出上月 cohort 的实测点 → 拟合 → 人工复核（对比上月参数，变动超过 15% 必须给出原因）→ 发布到 `dim_game`。

### 7.4 参数生效范围与回退规则（**按实现写，不是按设想写**）

**当前实现的事实**（`store.ts` → `recoveryRateFor(gameId)`）：

```ts
const cur = roiAt(k, g?.curveA ?? 0.2, g?.curveB ?? 0.15);
```

即查找关系是**两级**，不是三级：

```text
① 游戏级   dim_game(game_id).curve_a / curve_b            ← 唯一实际生效的参数层级
② 全局兜底 curveA = 0.20, curveB = 0.15                    ← 仅当取不到游戏元数据时触发
```

| 事实 | 说明 |
|---|---|
| **只按游戏取参数** | 引擎只消费 `GAME_MAP.get(gameId).curveA / curveB`，数据里 16 个游戏各有独立参数 |
| **取不到 → 全局硬编码默认值 `(0.20, 0.15)`** | 就是 `roiAt()` 的兜底入参。**没有「回退到平台均值」这一层** |
| **该兜底路径在实际数据中不会触发** | 84 个投放组合（`CAMPAIGNS`）的 `gameId` 全部能在 `GAME_MAP` 中命中，属于**防御性代码**（防止未来新增游戏只配了元数据漏配曲线时崩溃） |

> ⚠️ 措辞纪律：`docs/01` §3.4 曾提出「分平台 × 分游戏独立，取不到时回退到平台均值」的**设计意图**。**该平台级回退在代码中并未实现**——本节以代码为准。若后续要落地平台级回退，需在取数层显式增加该分支，并同步更新本节。

**契约层的数据结构**：`CurveParam{ scope: 'global'|'platform'|'game', scopeId, scopeName, curveA, curveB, mape, sampleDays, enabled }` 保留了 `platform` 这个 `scope` 取值，参数配置页（`/settings`）按此结构展示，属于**为将来扩展预留的契约**；落地时需把回退链补进取数层，并补上「命中条件」（建议：游戏级回测样本 ≥ 60 天且 MAPE ≤ 25%，不满足才回退）。

### 7.5 ROI 三指标统一为「累计口径」（全站一致，必读）

`buildMetrics()` 中这三个指标的分子分母**全部取自累计字段**（`cumExp` / `cumSpend` / `cumAccrual`），与筛选期间的长度无关：

```text
forecastRoi  = 累计预估总回收 cumExp    / 累计投放消耗 cumSpend      ← 不随 startMonth 变化
actualRoi    = 累计已确认回收 cumAccrual / 累计投放消耗 cumSpend      ← 不随 startMonth 变化
recoveryRate = 累计已确认回收 cumAccrual / 累计预估总回收 cumExp      ← 不随 startMonth 变化
```

实现细节：`finishAgg()` 在聚合结束时取**区间末月**的 `cumSpend / cumAccrual / cumExp{90,180,360}` 字段，因此「区间末月」之前的筛选范围只影响流量（`spend` / `revenue` 等本期指标），不影响这三项。

| 口径 | 含义 | 是否随筛选期间变化 |
|---|---|---|
| 本期口径（如 `spend`、`accrualRevenue`、`operatingProfit`） | 筛选区间内发生的量 | ✅ 变化 |
| **累计口径（`forecastRoi` / `actualRoi` / `recoveryRate`）** | **自数据起点（2024-01）到区间末月的存量盘子累计表现** | ❌ **不变** |

**两条必须遵守的表述纪律**：

1. **UI 与文档中一律写「累计」二字**（「累计预估 ROI」「累计实际 ROI」「累计回收完成度」），避免被误解为「本期的 ROI」。
2. **按单月筛选时，这三个数描述的仍是该范围内存量盘子的累计表现**，不是当月新投的钱的表现。实测验证：把筛选期间收窄为单月 `2026-06`，`forecastRoi / actualRoi / recoveryRate` 依旧返回全量累计值（1.4619 / 1.3605 / 0.9306），与默认 12 个月期间完全相同——因为区间末月仍是 2026-06。

> 设计动机：对齐现有系统的「累计 ROI」口径，使看板数字与业务方既有认知一致。若要新增「本期 ROI」，应另起字段名（如 `periodRoi`），不要复用这三个字段。

## 八、模型的已知局限（必读）

### 8.1 对数曲线的三个结构性假设

| # | 假设 | 什么时候会失真 | 缓解手段 |
|---|---|---|---|
| 1 | **回收永不停止**：`ROI(n) = a·ln(n)+b` 在 `n→∞` 时无上界 | 所有用户终将流失，真实 LTV 曲线会**收敛/衰减**。对数曲线会把 D360 之后的价值算得偏高（虽然后期斜率极小：D360 后每 100 天只增加约 0.055） | 明确标注「预估窗口 90/180/360 天」；不做 360 天以外的外推；`RECOVERY_MAX_DAY = 365` 在工程上硬截断 |
| 2 | **历史曲线可外推**：用过去 cohort 的参数预测未来 cohort | **版本更新 / 素材结构变化 / 平台政策变化**都会让新 cohort 的曲线与历史不同。这类变化是**阶跃**的，不是渐变的，回归模型无法预判 | ① 按月重拟合（§7.3）；② 对话式预警：`actualRoi / forecastRoi` 偏离 > 10% 时提示「曲线可能失真」；③ 参数变更留痕，可回溯 |
| 3 | **同游戏内曲线同质**：一个游戏的所有投手/素材共用一组 `curveA/curveB` | 同一游戏的不同素材首日 ROI 可能差 2 倍以上，但看板按游戏聚合会抹平差异 | 已知局限；素材级曲线需要更细的 `campaign_id` 粒度数据，属后续迭代 |

### 8.2 「只有首日能算」——来自现有系统的明确结论，必须如实引用

现有系统的 **`roi-scenario` 模块**明确指出：**只有首日 ROI 能可靠计算，90 / 180 / 365 日 ROI 不能靠首日三项外推。**

这条结论对本看板有两层含义：

1. **不能做的事**：不要设计「用户填一个 D1 回收率，系统自动推算 D360」的功能。从 D1 到 D360 之间没有任何可验证的信息，任何外推都是猜。D1 → D90 的倍增系数在不同游戏间从 5.2 倍（神域卡牌 0.170→1.115）到 10.9 倍（成语消消 0.050→0.545）不等，**没有稳定关系**。
2. **本站的做法**：**用业务给出的多锚点标定曲线，而不是从 D1 推算 D360**。具体地：

```text
✅ 本站做法：业务给出 (D1, D90) 两个锚点 → 两点标定 curveA / curveB → 曲线可解释、可审计
❌ 不采用：  业务只给 D1 → 用某种倍增系数推算 D90/D180/D360
```

这正是 §2.2 两点标定法存在的理由——它需要**两个业务锚点**，而不是一个。参数配置页要求配置 `curveA` 与 `curveB` 两项（对应两个锚点），也是同一逻辑。

### 8.4 预估值与实际的偏差将主要来自缺失数据源

`docs/03` §1.1 已说明：**预付成本 / 流量主收入 / 广告金 / 分成收入四项目前没有真实外部数据源**。这意味着：

| 影响面 | 说明 |
|---|---|
| 应确认收入（经营口径） | 由 `accrualRevenue × iaaShare × liuliangzhuShare` 等**占比系数**拆分而来。占比一旦不准，三科目全部错，且**错误无法通过看板自身发现**（没有任何外部数据可对账） |
| 到账收入（账面口径） | 用 `settleLagDays` 固定滞后模拟，真实结算周期会浮动且各渠道不同 |
| 现金缺口 / 应收未收 | 依赖预估总回收，与曲线参数强耦合 |
| **结论** | 在补齐这四个数据源之前，**口径差额（`profitGap`）与三科目结构分析的置信度应视为「低」**，看板文案与汇报口径需要明确标注。相比之下，投放消耗与人工成本的置信度是「高」（有真实源或已结构化） |

| 消除项目 | 963.0 | 941.1 | −21.9 |
| 休闲竞技项目 | 430.4 | 436.7 | +6.3 |

**含义**：业务轴上的「某项目亏了」这个结论，**部分是分摊规则的产物**，不是纯粹的业务事实——两种口径下差额可达 ±330 万元，足以让「盈利/亏损」的结论翻转。任何基于业务轴的项目考核/止损决策，都必须同时说明当期使用的分摊基数。这也是 §9 第 2 条必须由业务确认的原因。

## 九、待业务确认的口径问题清单

| # | 问题 | 影响 | **推荐方案** | 决策人 |
|---|---|---|---|---|
| 1 | **广告金中「仅可抵扣投放」的部分是否计入收入？** | 若计入，收入虚高但对应资产真实存在（可抵扣未来投放）；若不计入，收入口径更保守但会低估经营成果 | **建议：计入收入，同时计入预付资产**（即「收入 + 资产」双记，避免净额法掩盖体量）。需在 `fact_revenue_daily.withdrawable` 字段区分，看板可切换「含/不含不可提现广告金」两种收入口径 | 财务 + 业务负责人 |
| 2 | **预付成本的摊销规则：按消耗进度 vs 按时间直线？** | 按消耗进度 = 与投放节奏绑定（符合业务实质）；按时间直线 = 简单但与实际使用脱节 | **建议：按消耗进度摊销**（`本期摊销 = 本期消耗 × 该账户均价`），因为预付的用途就是投放，时间直线会在暂停投放时仍计提成本 | 财务 |
| 3 | **项目管理费用分摊基数：投放消耗占比 vs 人头占比？** | 见 §8.5：公司合计不变，项目层利润分布可差 ±330 万 | **建议：默认投放消耗占比**（与管理费用的真实驱动力一致），参数配置页保留人头占比开关，并在页面明示当期口径 | 业务负责人 + 财务 |
| 4 | **预估曲线按平台标定还是按平台 × 游戏标定？** | 按平台：样本多、稳健，但抹平游戏差异；按游戏：精确，但小游戏样本天数不足 | **建议：以「平台 × 游戏」为目标粒度，逐级回退**（游戏样本 < 60 天 → 回退平台均值 → 再回退全局），并在参数配置页展示每个范围的样本天数与 MAPE。⚠️ **注意：这是建议方案，当前引擎只实现了「游戏级 → 全局兜底」两级**（详见 §7.4），平台级回退需先在取数层实现 | 算法 + 业务 |
| 5 | **流量主收入到账滞后是否影响账面利润的期间归属？** | 若按到账日归属，账面利润永远滞后 30~60 天，季度对比失真；若按应计日归属，账面利润就不再是「银行流水口径」 | **建议：账面口径严格按到账日（维持「银行流水」定义不变），另开「应计口径」列做期间对比**。两列并列展示，不做合并 | 财务 |
| 6 | **项目奖金的归集口径：按发放对象组织归集，还是按奖金指向的项目归集？** | 前者进入组织轴人的成本；后者进入业务轴项目的成本。同一笔钱不能两边都算 | **建议：默认按「奖金指向的项目」直接归集到业务轴**（`fact_labor_cost_monthly.bonus_project_id`），组织轴同步显示但**不重复计入公司合计**；无法指向项目时按组织归集 | 人事 + 财务 |
| 7 | **平台返点率（`rebateRate`）是否要单独建账？** | 当前广告金完全由 `iaaShare × (1−liuliangzhuShare)` 推导，`rebateRate` 未被使用。若返点要单独核算，需要新增数据通路 | **建议：单独建账**——返点是「投放额 × 固定比例」的确定性收益，性质与不确定性回收不同，混在广告金里会让广告金科目失去解释力 | 财务 |
| 8 | **准备金/坏账：应收未收（`receivable`）是否要计提减值？** | 若部分渠道结算存在争议或坏账，`receivable` 会高估资产，进而高估经营利润 | **建议：对账龄 > 90 天的 `receivable` 计提 5% 减值准备**，在看板上作为独立一行展示（不冲减收入，只提示风险） | 财务 |
| 9 | **当月固定成本摊薄规则是否要按「已过自然日 / 当月自然日」？** | 引擎现按 18/30 = 0.6 摊薄人工与办公费，使「当月已实现利润」与「当月全月预估」可对照。但工资是**整月一次性发生**，按日摊薄是 period-to-date 惯例而非会计准则 | **建议：保留按日摊薄作为管理口径**，同时在财务口径下另列「整月全额」一列；并在页面上注明「当月数据截至 18 日，固定成本按 60% 计入」 | 财务 |
