## 一、业务背景与核心命题

公司是**游戏公司**，主营模式为「买量投放 → 游戏内变现」：

```
资金投入（投放充值 / 预付 / 人工） ──► 买量获取用户 ──► 用户游戏内行为
                                                          │
                            ┌─────────────────────────────┴─────────────────────────────┐
                            ▼                                                           ▼
                    IAA 广告变现                                               IAP 内购变现
              （流量主收入、广告金）                                        （应用商店/渠道分成收入）
```

由此产生**两个必须同时看的利润口径**：

| 口径 | 定义 | 数据基础 | 特征 | 现状 |
|---|---|---|---|---|
| **账面利润** | 根据银行账户当前**实时流水**核算的利润 | 银行流水 / 已收已付 | 精确、可审计，但**严重滞后** | 已有系统支持（业务财务看板），本次不重建 |
| **经营利润** | 根据**投资额 + 预估回报率**核算的公司真实经营成果 | 投放成本 + 预估 ROI 回收曲线 + 人工/管理成本分摊 | 及时反映经营质量，但含预估成分 | **本次要补齐的核心能力** |

**一句话命题**：账面利润回答「公司账上现在赚了多少」，经营利润回答「公司这段时间做的生意，最终赚不赚钱」。

两者之间的差额本身就是最重要的经营信号：
- 差额为正且扩大 → 处于**放量投入期**，钱花出去了还没收回来（健康还是危险，要看预估 ROI）
- 差额为负 → 回收超预期 / 或存在**应付未付**（如投放款未结、奖金未发）

## 二、数据源盘点（执行项 1）

### 2.1 管理数据（Management Data）

| 大类 | 明细项 | 口径 / 取数逻辑 | 数据来源 | 归属成本科目 |
|---|---|---|---|---|
| **人工成本** | 工资 | 当月应发薪资（含基本+绩效） | 人事/薪酬系统、工资表 | 人工成本 |
| | 医社保 | 公司承担部分 | 社保申报表 | 人工成本 |
| | 个税 | 代扣代缴个税（公司现金流口径） | 个税申报表 | 人工成本 |
| | 项目奖金 | 按项目/游戏发放的奖金 | 奖金核算表 | 人工成本（**可按项目直接归集**） |
| **管理费用** | 福利费 | 团建、节日福利、体检等 | 费用报销系统 | 管理费用 |
| | 办公费 | 房租、水电、办公用品、软件订阅等 | 费用报销系统 / 合同台账 | 管理费用 |

**关键说明**：
- 管理数据通常**按月**产生，粒度**天然比业务数据粗**（无法按天/按游戏拆分）→ 必须定义**分摊规则**（见 §4.3）。
- 项目奖金是唯一可以**直接归集到项目/游戏**的管理数据，其余需要按规则分摊。

### 2.2 业务数据（Business Data）

| 大类 | 明细项 | 口径 / 取数逻辑 | 数据来源 | 说明 |
|---|---|---|---|---|
| **业务成本** | 投放成本 | 媒体后台**当日实际消耗**（不是充值额！） | 腾讯广告 / 巨量 / 快手等媒体 API | 严格区分「充值」与「消耗」 |
| | 预付成本 | 已充值未消耗的余额、预付的渠道/素材/IP 费用 | 媒体账户余额、预付合同台账 | 形成「预付款资产」，按消耗进度转成本 |
| **业务收入** | 流量主收入 | 小游戏内激励视频/插屏/Banner 广告分成收入（微信/抖音流量主） | 流量主后台（微信小游戏、抖音小游戏） | 媒体结算周期通常 T+30~T+60 |
| | 广告金 | 平台返还的广告金 / 返点（如微信小游戏广告金、腾讯广告返点） | 平台结算单 | 需区分「可提现」与「仅可抵扣投放」 |
| | 分成收入 | IAP 内购流水经应用商店/渠道分成后的净收入 | 应用商店（App Store/华为/OPPO/vivo）、渠道对账单 | 约 30%~50% 被渠道抽成 |

### 2.3 数据源到看板的链路

```
媒体投放 API ─┐
流量主后台   ─┤
渠道对账单   ─┼─► 数据中台（ETL / 宽表）─► 经营分析看板
薪酬/费用系统 ─┤        │
银行流水     ─┘        └─► 账面利润（已有系统）
```

## 三、利润预估算法（执行项 2）

### 3.1 核心思想：从「当期消耗」到「全生命周期回收」

投放成本在**投放当天一次性发生**，但它带来的收入会在**未来 90~360 天**陆续回来。因此经营利润必须做**收入确认的时间匹配**。

### 3.2 回收曲线（现有 ROI 预估能力）

现有系统中已在使用的预估逻辑（`DigitalPublishingCenter/VersionInfoPanel.vue`）：

```
预估 ROI 使用对数函数走势：  y = a · ln(x) + b
  其中  x = 投放后天数（1, 2, 3, ... N）
        y = 第 x 天的累计回收 ROI
        a, b = 按平台 / 项目 / 游戏拟合的参数（a > 0，b 为初始回收基线）
```

**数学含义**：
- 对数函数天然刻画「早期回收快、后期趋缓」的买量回收规律；
- `x = 1` 时 `y = b`，即首日回收率（D1 ROI）；
- `x` 增大时 `y` 增速递减，天然收敛，符合用户 LTV 长尾特征；
- 由 `a, b` 可外推任意周期的累计 ROI：`ROI(n) = a·ln(n) + b`。

**由曲线推导利润的完整算法**：

```
① 单日投放成本：            cost(d)                   ← 媒体 API 当日消耗
② 该日投放的预估总回收：      rev∞(d) = cost(d) · ROI(N)      N = 90/180/360
   其中 ROI(N) = a · ln(N) + b   （按 平台×游戏 取参数）
③ 截至第 t 天的已回收：       rev_t(d) = cost(d) · ROI(t)
④ 本期应确认收入（权责发生制）：
       确认收入(本期) = Σ_{d ∈ 本期} rev_t(d)   ← 本期内各投放日的累计回收增量
                      + Σ_{d < 本期起点} [rev_{t2}(d) − rev_{t1}(d)]
                        ← 历史 cohort 在本期新回收的部分
⑤ 本期经营利润 = 确认收入(本期) − 本期业务成本 − 本期人工成本 − 本期管理费用
⑥ 未确认（应收未收）= Σ_d [ rev∞(d) − rev_t(d) ]   ← 存量用户的未来价值（资产）
```

**关键指标**：
- **回收完成度** = 已回收 / 预估总回收 —— 判断放量节奏是否健康
- **现金缺口** = 累计投放支出 − 累计回收收入 —— 就是账面利润与经营利润的差额主体

### 3.3 月度经营预估（需求 3：针对每个月做出预估分析）

按三层递进：

| 层级 | 场景 | 算法 |
|---|---|---|
| **L1 当月实时预估** | 月中看当月最终结果 | `当月预估 = 已过天数实际值 + 剩余天数 × 近 7 日均值 × 季节系数` |
| **L2 未来月度预估** | 未来 1~6 个月经营利润 | `未来月利润 = 存量 cohort 在该月的回收（由对数曲线逐月切片） − 该月预计投放成本 − 该月人工/管理成本（预算值）` |
| **L3 滚动全年预估** | 全年经营利润预测 | 已实现月份实际值 + 剩余月份 L2 预估汇总，输出乐观/中性/悲观三档 |

**预估质量校验**：
- **MAPE（平均绝对百分比误差）** = `mean(|实际 − 预估| / 实际)`，滚动回测最近 6 个月；
- **偏差归因**：区分「投放节奏偏差」与「回收效率偏差」；
- 曲线参数**按月重新拟合**，避免参数漂移。

### 3.4 待确认的口径问题（需业务确认）

1. 广告金中「仅可抵扣投放」的部分，是否计入收入？（本 MVP 按「计入收入 + 计入预付资产」处理）
2. 预付成本的摊销规则：按消耗进度摊销，还是按时间直线摊销？
3. 项目管理费用分摊基数：按投放消耗占比，还是按人头占比？（本 MVP 默认提供两种可切换）
4. 预估 ROI 参数是全局统一，还是**分平台×分游戏**独立？（本 MVP 默认分平台×游戏独立，取不到时回退到平台均值）
5. 流量主收入到账滞后天数，是否影响「账面利润」的期间归属？

## 四、看板信息架构与模块规划（执行项 3）

### 4.0 双轴下钻模型（重要设计决策）

需求给出的层级链是：`公司 → 中心 → 部门 → 小组 → 平台 → 项目 → 单游戏 → 单人(投手)`。

但实际上存在**两个正交的维度轴**——「平台/游戏」不是「小组」的下级，一个投手可以投多个平台、一个平台可以投多个游戏：

| 轴 | 层级 | 用途 |
|---|---|---|
| **A. 组织轴** | 公司 → 中心（研发/发行/中台/职能）→ 部门 → 小组 → 投手(人) | 回答「**谁**在赚钱」 |
| **B. 业务轴** | 公司 → 平台 → 项目 → 单游戏 | 回答「**什么**在赚钱」 |

**MVP 设计**：逐层下钻模块提供**可切换的下钻路径**，默认按需求给出的链条展示，同时支持组织轴 / 业务轴独立下钻，以及**「组织 × 业务」交叉分析**（如：发行中心-投放一组-张三 在 腾讯广告平台 投的《XX》游戏的 ROI）。

### 4.1 模块总览

| # | 模块 | 页面/区块 | 意义（回答什么问题） | 主要展现数据 |
|---|---|---|---|---|
| M1 | **全局筛选栏** | 全局 | 统一分析口径，所有模块联动 | 时间粒度（年/季/月）、期间选择、利润口径（账面/经营/双口径）、组织范围、平台范围 |
| M2 | **核心指标卡** | 经营总览 | 一眼看清公司经营结果 | 营业收入、营业成本、**账面利润**、**经营利润**、经营利润率、预估 ROI、现金缺口、预估偏差 |
| M3 | **双口径利润趋势** | 经营总览 | 账面 vs 经营的差距如何演化 | 月度双柱（账面利润/经营利润）+ 差额折线 + 累计曲线 |
| M4 | **组织利润贡献** | 经营总览 | 钱是哪些中心/部门赚的 | 中心/部门利润占比（旭日图/桑基图）、利润率热力 |
| M5 | **收入结构分析** | 经营总览 / 收入分析 | 收入从哪来 | 流量主收入 / 广告金 / 分成收入 三块：趋势、结构饼图、平台分布、游戏 TopN |
| M6 | **成本结构分析** | 经营总览 / 成本分析 | 钱花到哪去 | 业务成本（投放/预付）+ 人工成本（工资/医社保/个税/奖金）+ 管理费用（福利/办公）：结构树、趋势、分摊明细 |
| M7 | **逐层下钻表** | 逐层下钻 | 从公司一直下钻到投手 | 树形表格：每层 收入/成本/账面利润/经营利润/利润率/ROI/环比；支持任意层展开 + 右侧联动趋势 |
| M8 | **月度经营预估** | 月度预估 | 本月/未来几个月会怎样 | 当月实时预估（已过天数+剩余天数外推）、未来 6 个月滚动预估（乐观/中性/悲观）、预估 vs 实际偏差 |
| M9 | **Cohort 回收分析** | 月度预估 | 每个月的投放最终回收得怎么样 | 各月投放 cohort 的累计回收 ROI 曲线（对数曲线）、回收完成度、预计回本月份 |
| M10 | **投手人效榜** | 投手人效 | 哪个投手最能赚钱 | 单人：消耗、带来收入、账面/经营利润、ROI、人力成本、**人效比（利润/人力成本）**、排名趋势 |
| M11 | **预警与洞察** | 经营总览 | 哪里出问题了 | 规则引擎输出的预警：ROI 低于红线、回收完成度滞后、成本超支、人效异常、预估偏差过大 |
| M12 | **预估参数配置** | 参数配置 | 让老板/财务能调预估逻辑 | 回收曲线参数（a/b，分平台×游戏）、预估周期 N（90/180/360）、成本分摊规则、算法公式说明 |

### 4.3 成本分摊规则（MVP 默认）

| 成本项 | 归集方式 | 默认分摊基数 |
|---|---|---|
| 投放成本 | **直接归集**到 投手/小组/平台/游戏 | — |
| 预付成本 | 直接归集，按消耗进度转成本 | — |
| 项目奖金 | **直接归集**到项目/游戏 | — |
| 工资 / 医社保 / 个税 | 按人归集到部门/小组 | 直接归集（有人员归属表） |
| 福利费 / 办公费 | 间接费用，向下分摊 | 默认**按投放消耗占比**（可切「按人头占比」） |

### 4.4 核心指标口径表

| 指标 | 字段示意 | 公式 | 单位 |
|---|---|---|---|
| 营业收入（账面） | `cashRevenue` | 银行到账的流量主收入 + 广告金 + 分成收入 | 元 |
| 营业收入（经营） | `accrualRevenue` | 本期应确认收入（§3.2 ④） | 元 |
| 业务成本 | `businessCost` | 投放成本 + 预付成本（本期摊销） | 元 |
| 人工成本 | `laborCost` | 工资 + 医社保 + 个税 + 项目奖金 | 元 |
| 管理费用 | `adminCost` | 福利费 + 办公费 | 元 |
| **账面利润** | `bookProfit` | 账面收入 − 全部已付成本 | 元 |
| **经营利润** | `operatingProfit` | 应确认收入 − 业务成本 − 人工成本 − 管理费用 | 元 |
| 口径差额 | `profitGap` | 经营利润 − 账面利润 | 元 |
| 经营利润率 | `operatingMargin` | 经营利润 / 应确认收入 | % |
| 预估 ROI | `forecastRoi` | `a·ln(N) + b` | % |
| 实际 ROI | `actualRoi` | 累计已回收 / 累计投放成本 | % |
| 回收完成度 | `recoveryRate` | 已回收 / 预估总回收 | % |
| 现金缺口 | `cashGap` | 累计投放支出 − 累计回收收入 | 元 |
| 人效比 | `efficiencyRatio` | 经营利润 / 该人人力成本 | 倍 |
| 预估偏差 | `forecastMape` | mean(\|实际−预估\|/实际) | % |

## 五、MVP 交付范围与技术方案

- **技术栈**：Vue 3 + Vite + TypeScript + Element Plus + vxe-table + ECharts，Hash 路由，纯前端 Mock 数据（对齐团队既有前端系统规范）
- **数据**：全部使用 Mock，但**结构完全对齐真实数据模型**，后续替换为接口即可
- **交付**：7 个页面可跑通、可下钻、可切换时间与口径

### 暂不包含（后续迭代）

- 真实数据接入与 ETL
- 权限体系与数据行级隔离
- 预估模型的线上训练与自动参数拟合
- 移动端适配
