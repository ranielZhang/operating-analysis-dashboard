## 2. 已实现的 3 条需求对照表

### 需求 1 · 逐层下钻（公司 → 中心 → 部门 → 小组 → 平台 → 项目 → 单游戏 → 单人）

| 需求要点 | 落点页面 | 落点模块 | 实现方式 |
|---|---|---|---|
| 从公司一路钻到单人 / 单游戏 | `/drilldown` | `DrillTreeTable.vue` | `el-table` 懒加载树表，`row-key` + `:tree-props`，点击行按 `parentId` 向 store 取下一层 |
| 需求给的「单链」层级被拆成两条正交轴 | `/drilldown` | `DrillTreeTable.vue` + `useDrillSelection.ts` | 「组织轴」（公司→中心→部门→小组→投手）与「业务轴」（公司→平台→项目→游戏）**可切换**，因为平台/游戏不是小组的下级 |
| 任意层级的完整经营画像 | `/drilldown` | `DrillDetailPanel.vue` | 右侧侧栏展示选中节点的收入/成本/双口径利润/累计 ROI/人数/月度走势 |
| 「组织 × 业务」交叉分析 | `/drilldown` | `CrossMatrix.vue` | 行 = 小组或投手，列 = 平台，格 = 交叉指标（经营利润 / 累计预估 ROI / 投放消耗 / 人效比），含行合计、列合计与矩阵总计 |
| 全站口径联动 | 全站 | `AnalysisFilterBar.vue` + `useAnalysisFilter.ts` | 组织范围 / 业务范围 / 期间 / 粒度 / 利润口径 / 预估窗口 统一筛选，所有模块 `computed` 自动重算 |

### 需求 2 · 年 / 季 / 月三种时间粒度 + 双口径（账面 / 经营）对比

| 需求要点 | 落点页面 | 落点模块 | 实现方式 |
|---|---|---|---|
| 年 / 季 / 月粒度切换 | 全局 | `AnalysisFilterBar.vue` | `filter.granularity = 'year' \| 'quarter' \| 'month'`，`store.querySeries()` 按粒度自动分桶，标签为「2025年 / 2025Q3 / 2025年7月」 |
| 账面 / 经营双口径并列 | 全局 | `AnalysisFilterBar.vue` | `filter.basis = 'book' \| 'operating'`，切换后所有卡片、图表、表格的「利润/成本/收入」全部换口径；`Metrics` 同时恒算 `bookProfit` / `operatingProfit` 供对比 |

| 口径差额归因 | `/overview` | `ProfitBridge.vue` | 瀑布桥：从账面利润经预付余额、应收未收等科目拆到经营利润 |

## 4. 已知限制与待业务确认

> 以下逐条如实记录，不做美化。每条都标注了**影响面**与**建议动作**。

### 4.1 数据是纯前端确定性 Mock，没有后端

- 全站所有数字来自 `src/domain/store.ts`（单一数据真源），用 `mulberry32(hash01(...))` 生成**确定性**伪随机序列，
  因此同一筛选条件每次刷新结果完全一致，可复现、可回归。
- **没有网络请求、没有数据库、没有接口层**。刷新页面不会拿到新数据。
- 替换真实接口时**只需替换 `store.ts` 的取数层**（`CAMPAIGN_MONTH` / `ORG_OWN_COST` 的生成逻辑与
  `resolveScope` / `queryRows` / `metricsOf` / `forecast` / `cohorts` 的数据来源），
  上层页面与全部组件无需改动——这也是本次把取数全部收敛到 `store.*` 的收益。

### 4.2 只有投放消耗有真实数据源，其余关键科目全部缺失

| 科目 | 是否有真实外部数据源 | 现状 |
|---|---|---|
| **投放消耗** | ✅ 有 | 腾讯广告报表 API `daily_reports/get`，返回字段 `cost`，**单位是「分」**，入库需保留原始分字段、展示层统一换算成元（漏换算会出现 100 倍误差） |
| 投放消耗（其他平台） | ⚠️ 部分 | 巨量引擎 / 快手磁力 / 小米营销有报表 API，但结算滞后 30~60 天，偶有当日缺数 |
| **预付成本（充值额）** | ❌ 无 | 仅财务手工维护字段 |
| **流量主收入** | ❌ 无 | 仅手工维护字段 |
| **广告金收入** | ❌ 无 | 仅手工维护字段；含「仅可抵扣投放」部分，口径待确认（见 `§4.8`） |
| **分成收入** | ❌ 无 | 仅手工维护字段，依赖应用商店渠道对账单 |
| 人工成本 / 管理费用 | ❌ 无 | 由组织树 + 薪资规则推导，非真实薪税数据 |

- **影响面**：经营利润、账面利润、双口径差额、现金缺口、回收完成度的绝对值都建立在 Mock 之上，
  **只能看结构与趋势，不能用于对外报表或绩效考核**。
- `/datasource` 页面已逐源标注接入状态（`connected` / `partial` / `unavailable` / `unconfigured`）与真实接口名，
  避免把演示值当成真实接入。

### 4.3 曲线参数只有两级回退，没有平台级回退层

- 现状：`curveA` / `curveB` 挂在**游戏级**（`GameMeta`），取不到时回退到**全局兜底 0.20 / 0.15**。
- 需求文档（`docs/01` §3.4 第 4 条）要求的是 **平台 × 游戏 → 平台均值 → 全局** 三级回退，
  **「平台级均值」这一层没有实现**。
- **影响面**：新上线、尚未单独配置曲线的游戏会直接落到全局兜底值，可能与其所属平台的真实回收特征偏离较大，
  进而影响该游戏的经营利润与累计预估 ROI。
- **建议动作**：在 `dimensions.ts` 增加 `PLATFORM_MAP[x].curveA/curveB`，把回退链补成三级。

### 4.4 16 个游戏里有 8 个的 `paybackDays` 与曲线反解回本天数偏差 > 60%（Mock 参数不自洽）

- 校验方法：曲线 `ROI(n) = curveA·ln(n) + curveB`，令 `ROI(n) = 1` 反解 `n = exp((1 − curveB) / curveA)`，
  与 `GameMeta.paybackDays` 比较。实测结果：

| 游戏 | 声明 `paybackDays` | 曲线反解 | 偏差 |
|---|---|---|---|
| 成语消消 | 190 天 | 5633 天 | 96.6% |
| 乡村生活 | 170 天 | 2523 天 | 93.3% |
| 热血传奇 | 75 天 | 17 天 | 77.7% |
| 无尽塔防 | 155 天 | 665 天 | 76.7% |
| 糖果消消乐 | 90 天 | 23 天 | 74.8% |
| 疯狂射箭 | 95 天 | 32 天 | 65.9% |
| 星海卡牌 | 160 天 | 431 天 | 62.9% |
| 花园消消乐 | 100 天 | 40 天 | 60.3% |

- **偏差 > 60% 的为 8 / 16 个**（任务书里写的 10 个与实测不符，此处以**实测 8 个**为准）。
  其中 4 个游戏（成语消消、乡村生活、无尽塔防、星海卡牌）按曲线在 **360 天内根本无法回本**。
- **影响面**：`paybackDays` 目前只用于「Cohort 表 / 预警文案」的展示与说明，
  **不参与回收曲线的数值计算**（计算只用 `curveA` / `curveB`），因此**不影响任何金额**；
  但同一页面上「预计回本天数」（由曲线插值得出）与「反向校验的声明天数」会互相矛盾，**会被业务方质疑**。
- **建议动作**：接入真实回收数据后重新拟合曲线，并由拟合结果**回填 `paybackDays`**，或以曲线反解值取代手工声明值。

### 4.5 业务轴的成本池按消耗占比分摊 ⇒ 组织 × 业务交叉矩阵的加总 ≠ 公司加总

- 机制：`store` 在业务维度（平台 / 项目 / 游戏）上是把公司的成本池**按各业务的投放消耗占比分摊**下去的；
  同一个人工成本会因为「同时在多个平台投放」而被**重复计入多个平台列**。
- **影响面**：`/drilldown` 的「组织×业务交叉矩阵」中，
  **按平台方向加总 ≠ 公司合计**（人工成本会随平台维度重复计入）。
- **已做的处理**：矩阵内已显式标注口径（「格值＝组织范围 × 平台的期间合计；行/列合计与右下角为矩阵内加总」），
  并在矩阵内单独重算比率类指标（不直接把比率相加）。
- **待业务确认**：人工成本是否应改为按「实际投入该平台的人头」归集而非按消耗占比分摊——
  这决定了矩阵是否应该做到「可加总」。

### 4.6 `MAPE` 在实际利润为负时会失效，正式落地建议改用 WAPE / sMAPE

- 现状：`/settings` 曲线参数表里的「拟合 MAPE」是按游戏 id 生成的**确定性演示值（3%~12%）**，
  不是真实回归拟合结果，界面上已明确标注「演示值」。
- **口径缺陷**：`MAPE = mean(|实际 − 预估| / 实际)` 在分母（实际利润）为 **0 或负数**时无意义或爆炸。
  本业务里**单游戏 / 单投手经营亏损是常态**，因此 MAPE 在正式落地时不可直接用。
- **建议动作**：改用 **WAPE**（`Σ|实际−预估| / Σ|实际|`）或 **sMAPE**，并对亏损期单独出「偏差方向」归因
  （投放节奏偏差 vs 回收效率偏差），而不是只给一个百分比误差。

### 4.7 账面利润滞后于经营利润，主因是结算滞后

- 平台结算滞后（`settleLagDays`）：腾讯广告 **45 天**、巨量引擎 30 天、快手磁力 30 天、小米营销 **60 天**。
- 收入侧同样滞后：流量主 / 广告金 / 分成三项收入均非实时到账。
- 结果：**投放消耗在投放当天一次性发生，收入却在未来 90~360 天陆续回来**，
  因此账面利润天然滞后于经营利润，两者差额（`profitGap`）是**结算时间差**而非经营质量差。
- **影响面**：`/overview` 的「现金缺口 = 预付余额 + 应收未收」会被放大；
  短期（<1 个结算周期）的口径差额**不能解读为盈利恶化**。
- **已做的处理**：`CashGap` / `receivable` 标注为「时点」口径，
  双口径差额在 `ProfitBridge.vue` 里做了科目归因，预警面板也区分了「放量投入期」与「回收恶化」。

### 4.8 待业务确认的口径问题（来自 `docs/01` §3.4，本 MVP 选择了默认处理）

| # | 问题 | MVP 当前处理 | 影响 |

| 1 | 广告金中「仅可抵扣投放」的部分是否计入收入？ | 计入收入 **且** 计入预付资产 | 会同时抬高收入与预付余额，可能高估经营利润 |

### 4.9 交叉矩阵的口径近似与恒等式残差项

1. **组织 × 业务交叉矩阵的合计行/列的「累计口径比率」是反解值，存在口径近似。**
   `CrossMatrix.vue` 用 `spend / forecastRoi` 去反解「累计消耗」，该式**仅在「筛选区间等于全部历史」时成立**；
   默认筛选为近 12 个月，因此矩阵的**行合计 / 列合计 / 右下角总计**的「累计预估 ROI、回收完成度」与各格的真值
   不完全一致。**格值本身（`store.metricsOf` 直取）是准确的**，失真的只有合计层。
   - 根治方式：让 `Metrics` 暴露 `cumSpend` / `cumExp`（`FlowAgg` 内部已有这两个字段，只是未对外输出），
     合计改为直接累加而非反解。这需要改动 `domain/store.ts` 的**输出契约**，超出 A20 的收尾授权范围，**故未改**。
   - 已做的缓解：无投放期（`cumSpend === 0`）时不再输出伪造的 `0.00`。
2. **口径差额瀑布图的「③ 期间错配」柱恒为 0，其「期间错配」告警分支是死代码。**
   代数上 `item3 = profitGap − item1 − item2 ≡ 0`，因为
   `profitGap = accrualRevenue − spend − cashRevenue + prepay`，而 `item1 + item2 = accrualRevenue − cashRevenue + prepay − spend`，
   两者恒等。同理 `ProfitBridge.vue` 里那段「开发期断言」（`import.meta.env.DEV` 下的 `watch`）也**永远不会告警**。
   - 该柱可视化为零高、不影响读数，且它是「恒等式成立」的可视证据（badge 显示「已平衡」），**故保留未删**；
     若后续口径变更（例如引入第三类差异），这个分支会自然生效。
